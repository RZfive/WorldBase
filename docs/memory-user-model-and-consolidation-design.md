# WorldBase：用户画像、记忆生命周期与“做梦”整理架构

- 日期：2026-09-29
- 状态：架构提案，**尚未实现**本文新增模块、协议与自动维护策略。
- 基线：当前工作树，包括尚未提交的记忆召回、向量分批、来源展示修复。
- 范围：同一 WorldBase 用户配置内的多 Agent 记忆；跨设备同步另行设计。
- 关系：延续 `docs/shared-memory-embedding-architecture.md` 的 SQLite 主库＋派生向量索引，补齐事实治理、画像、维护和效果验证。旧文档中的目标能力不等于当前代码已经具备。

## 1. 核心结论

不要把下一步定义为“每天让 AI 删除一些记忆”。应建设：

> 有证据的事实 → 小而稳定的用户画像 → 按任务选择上下文 → 在行动中使用 → 从纠正与结果学习 → 可审核、可回滚的增量整理。

向量库只负责寻找候选，不负责决定什么是真的、应该保留多久、谁有权看，或用户当前究竟偏好什么。

“了解用户”至少体现为：新会话沿用已确认的偏好；能区分用户本人、他人、假设和提问；知道偏好的适用场景；明确纠正后下一轮生效；不会把 AI 的推测当成用户事实；用户要求忘记后不再从旧材料自动学回来。

## 2. 现有机制：已实现与缺口

### 2.1 当前删除

`harness-rs/crates/memory/src/lib.rs::delete_workspace_memory`：

1. 在主库事务中删除 `memory_entries`、FTS 记录、对应的 embedding 文档和任务。
2. 记录 `forget` 审计事件。
3. 清理各 generation 的派生向量。向量删除失败时有墓碑机制；召回还会回读主表验证，所以不存在的主记录不能继续作为有效命中。

当前这是**记忆条目的硬删除**，不是完整的跨来源遗忘：不等于删除原始聊天、所有引用副本、备份或外部供应商日志。现有 `forget` 事件按条目 ID 记录，尚没有阻止未来从旧聊天重新抽取同一事实的通用屏障。

### 2.2 当前 AI 整理

入口在设置页 `compactMemory()`，经 `memory:compact` 调用：

- `electron/main-process/ai/memory-compaction.ts` 扫描最多 50,000 条。
- `memory-compaction-plan.ts` 按 scope/type 分组，每批最多 40 条。
- 聊天模型生成 `deleteIds / mergeGroups / updates`。
- Rust `compact_workspace_memories` 执行删除、合并、更新。

已有保护：限制计划涉及的 ID；拒绝跨 scope/type 合并；整理删除时跳过 pinned 条目。

**但这仍然是人工触发的“生成计划后直接应用”，不是完整的后台学习系统：**

- 确认的是“是否开始整理”，不是对具体变更逐项确认。
- pinned 阻止整理删除，不等于禁止合并或 updates 改写其内容。
- 没有基于事实 revision 的过期计划拒绝机制。
- 合并沿用目标记录的来源，不能完整保留所有成员的证据关系。
- `serializeMemoryEntryForAi` 发送裁剪后的摘要/详情，没有把新增的 `sourceText` 作为证据传入整理模型。
- 未发现将此整理器接入空闲调度的内置链路。

### 2.3 必须先处理的风险

当前整理提示词把“与软件工程/当前 Agent 工作无关的知识”列为删除对象。

这不是通用个人助理可以采用的规则。对编码 Agent 暂时无关的“喜欢吃苹果”，仍可能是对用户重要的长期偏好。当前 `memory_add` 写入的个人事实也可能被标成 `knowledge`，不能靠类型名避免误删。

**因此，不能直接把现有 AI 整理挂到定时任务上。**

其他缺口：

- 表中已有 status、expires_at、evidence_count 等字段，但 Rust `WorkspaceMemoryEntry` 和普通写入路径尚未完整承载这些治理信息。
- 召回已有 active/到期过滤，但缺少完整的失效、替代、归档工作流。
- 没有“召回了／注入了／实际采用了／被用户纠正”的效果事件链。未发现召回主动维护 `last_used_at` 等字段的完整闭环。
- 自动提取仍主要是规则和助手回答中的信号词，不能替代有证据的用户模型。
- 旧 `memory.add/search` RPC 仍读写 `memories`，而桌面工作区及模型工具使用 `memory_entries`；兼容入口还需要归一化，不能假定所有客户端都已共享同一契约。

## 3. 借鉴 Hermes 与 Codex，但不混淆机制

以下仅描述核实过的公开能力，不推断未公开实现。

### Hermes：小型常驻记忆＋按需历史＋技能维护

Hermes 将个人画像放在 `USER.md`，其他核心笔记放在 `MEMORY.md`，以有容量限制的会话快照注入；历史细节由 `session_search` 按需找回。容量不足时工具报错，让 Agent 整理后再写，而不是静默丢记录。[H1]

其后台 review 可以提议记忆/技能改动；文档明确区分直接保存与待批准写入，后台替换/删除有更谨慎的批准与目标校验。[H1]

**Curator 主要管理技能，不是等同于用户记忆清理器。** 它区分陈旧、归档、合并，支持 dry-run、审计与恢复；自动归档和可选的 LLM 整合也是不同阶段。[H2]

借鉴：小型画像常驻、历史按需读取、学习与治理分离。不能把技能的低使用率归档规则原样用于用户偏好，也不能照搬多个 Agent 同写两个 Markdown 文件的存储形态。

### Codex：显式规则与生成记忆分开

OpenAI 官方文档将本地 Codex memories 与 ChatGPT memory 区分；本地记忆来自符合条件的历史会话，通过后台处理保留有用信息。读取记忆和让会话贡献新记忆可以分别控制，抽取与整合也有独立模型配置。必须一直遵守的项目规则仍应放在 `AGENTS.md` 或受版本控制的文档中，而非仅依赖生成记忆。[C1]

借鉴：显式规则优先、后台增量整合、证据可追溯、用户控制读写。这里不把“做梦”说成 Codex 某个未公开算法的名称。

## 4. 目标分层

| 层 | 内容 | 使用方式 | 默认生命周期 |
|---|---|---|---|
| 工作上下文 | 当前请求、进行中的步骤、最近工具结果 | 当前任务内使用 | 完成后移出热上下文 |
| 用户画像 | 语言、交互习惯、明确喜好、限制条件 | 小型核心常驻；其他类别按意图直读 | 明确更新或遗忘前保留 |
| 项目与决策 | 项目约束、已采用方案、决策理由、环境版本 | 按项目和任务召回 | 随项目状态与版本变化 |
| 历史事件与证据 | 用户原话、关键讨论、任务结果、来源片段 | 按需搜索并回读证据 | 依用户设置保留/归档 |
| 可复用技能 | 经过验证的操作方法、失败规避、适用条件 | 先检索技能目录，再加载技能 | 验证、修订、陈旧化、归档 |

长期目标和任务状态继续由现有 Goal/Task Service 持有。记忆保存引用、决策和经验，不另造一份会过时的“任务完成状态”。

```text
用户消息／明确纠正／已验证任务结果
                   │
          候选抽取 + 证据定位
                   │
         Rust Memory Service
   权限 · 类型 · 证据 · 版本 · 遗忘屏障
                   │
        ┌──────────┼──────────────┐
        ▼          ▼              ▼
    事实主库    画像投影       历史摘要／技能提案
        │          │              │
        └──────────┼──────────────┘
                   ▼
           Memory Context Builder
    核心画像 + 类别直读 + FTS/向量 + 原始证据
                   │
                   ▼
          Agent 回答和执行 → 结果／纠正日志

空闲维护：新增证据 → 整理提案 → 校验/审批 → 原子应用
                                     │
                            更新画像、索引与审计
```

继续使用 SQLite＋FTS5＋sqlite-vec。现阶段不为“做梦”另引入向量服务器或图数据库。

## 5. 事实、证据、画像必须是三件事

### 5.1 原子事实

以下为拟议结构，不是现有 DTO：

```json
{
  "id": "fact_apple_preference",
  "subjectId": "user:<authenticated-user>",
  "scope": { "type": "user", "id": "<authenticated-user>" },
  "kind": "preference",
  "key": "diet.apple.affinity",
  "value": "like",
  "assertionType": "user_explicit",
  "context": {},
  "status": "active",
  "revision": 1,
  "evidenceIds": ["evidence_user_message_1"],
  "validFrom": "<message-time>",
  "validUntil": null,
  "protection": "explicit_user_fact"
}
```

设计要求：

- 主体不能仅凭出现“我”判定：当前用户、其他发言人、被转述的人分别建主体。
- source role、权限、protection 由服务端可信上下文设置，不能让 LLM 自行声称“已确认”。
- 明确偏好、约束、环境事实、模型推断分开；没有证据的推测只能 pending，不能进入核心画像。
- 多值偏好不误判为冲突：“喜欢香蕉”不否定“喜欢苹果”；“现在不喜欢苹果了”才替换对应命题。
- 全局默认、项目例外、临时条件可以同时存在。本次要求“详细说明”不代表永久取消“通常简洁”。
- 来源未知的旧记录保留 legacy 标记，不能因为内容看起来确定就伪装为用户已确认。

### 5.2 独立证据

证据引用真实消息或产物，至少包含：稳定 message/artifact ID、作者身份、内容版本/hash、片段位置、时间、访问范围。

`sourceText` 保留为兼容展示，不再承担全部溯源责任。一个事实可有多个证据，一个消息也可支持多个事实，采用关联表而非合并时只保留目标记录的来源。

Rust 对话同步可能重建消息序号，证据不能只依赖会变化的自增 ID；应使用稳定逻辑消息 ID，附内容 hash。无法可靠恢复旧来源时标为不可追溯，不能猜测关联。

同一条消息重跑抽取、助手复述、或事实被召回，不增加“独立证据次数”。

### 5.3 用户画像是可重建投影

画像由当前有效事实编译，不是另一份可被模型任意覆盖的长总结。

初期建议核心画像预算 300–600 tokens；包括语言、交互规则和重要长期约束。饮食、出行等具体类别不必始终全文注入，但应有类别目录，并支持直读。

每段画像内容都能追溯 fact ID/revision；事实改了、被忘记了，画像必须失效并重建。可导出用户可读的 `USER.md`，但数据库仍是事实来源；导出文件不能成为第二个自动写入主库。

会话可缓存画像快照以降低重复成本，**纠正和遗忘不能等到下一次新会话**：下一次模型调用前重建相关上下文，或注入明确的版本更新并移除旧内容。

## 6. 怎样让记忆真正参与回答和行动

### 6.1 Context Builder 不只做向量搜索

顺序建议：

1. 验证用户、Agent、项目与目标受众权限。
2. 注入必要的核心画像和当前项目规则。
3. 识别是否是用户属性/偏好查询；若是，优先读取对应画像类别。
4. 对项目事实、历史事件执行词法＋向量候选召回，按类型、来源、适用条件和时间重排。
5. 不足时搜索历史会话，回读授权证据；技能先检索目录再按需加载。
6. 输出受预算限制、带 ID/来源/有效期的证据包，交给 Agent 决策。

个人事实查询不应该要求用户在问题里说出答案：

```text
“我喜欢吃什么？”
  → personal_profile / diet
  → 读取当前 diet 类别事实
  → 得到 apple=like
  → 回答“你喜欢吃苹果”
```

这里不需要依赖“我喜欢吃什么”和“苹果”的向量距离。Embedding 失效时，已知画像仍可正常使用。

### 6.2 证据约束

- 用户本次明确要求优先于长期默认偏好，但并不自动改写长期记录。
- 生成记忆作为带来源的数据，不作为高权限系统指令；技能也不能绕过工具权限。
- 用户事实、可信工具验证、助手建议和外部文档各自标注来源。
- “曾经没搜到”不是事实不存在的证据，不能写回为否定画像。
- 信息不足时承认不知道或只问一个必要问题，不从类似人群推断用户属性。

### 6.3 效果回流

区分以下事件：

```text
retrieved → injected → declared_used → outcome_observed
                                      ├─ user_confirmed
                                      ├─ user_corrected
                                      ├─ task_verified
                                      └─ unknown
```

模型声称“用了记忆”不等于实际有效；任务成功也不能自动证明所有注入的个人事实正确。用于排序的帮助程度需结合明确纠正、约束遵循和可验证结果，并标明无法归因的情况。

## 7. “做梦”维护：先提案，后受控应用

本文的 Dream Worker 是**低优先级、增量的整理任务**，不是重读所有聊天并自由改写用户。

### 7.1 触发策略

以下是建议初值，需配置与评测，不是现有行为，也不是 Hermes/Codex 的默认参数：

- 明确“记住/改为/忘记”：前台立即走事务，不等待后台。
- 自然任务结束或会话空闲：处理新增证据。
- 空闲约 10 分钟，且有约 20 个新增待处理事件、冲突或容量压力：安排一次小批整理。
- 没有新证据，不调用模型；正在对话、预算不足、用户关闭后台学习时延后。
- 每次先限制为约 20 个候选变更，有时间、token 和费用上限；前台请求可中止后台工作。
- 更深的跨任务技能整理另外调度，不和用户画像批量删除绑在一起。

### 7.2 执行流程

1. **取租约与快照**：按用户/项目分区，记录数据 revision 和增量游标。
2. **收集候选**：只读取新增、授权、未被遗忘屏障排除的证据；屏蔽密钥和不应学习的临时内容。
3. **聚类与冲突分析**：先按主体/作用域/命题键，再用相似度找可能重复者；相似不代表可合并。
4. **生成变更计划**：新增、去重、替代、归档、技能提案、画像重编译；必须提供证据和理由。
5. **确定性校验**：ID、revision、作用域、证据、用户保护、时间条件、指令注入和预算。
6. **风险分流**：低风险可自动应用；高风险进入待确认；不允许后台物理删除用户事实。
7. **短事务提交**：事实/关系/审计/索引 outbox 一起提交；LLM 调用不占数据库写锁。
8. **异步更新投影**：画像、FTS、向量；失败标为待更新，不伪报“已完成”。
9. **写报告与推进游标**：只报告实际提交的变化，失败可重试且幂等。

只要快照之后用户修正或遗忘了目标记录，旧计划就不能覆盖它；必须重新评估。模型只能提出变更，Rust Validator 才能授权执行。

### 7.3 权限矩阵

| 变化 | 初期默认策略 |
|---|---|
| 同作用域、同事实的完全重复证据去重 | 自动，保留证据关系 |
| 已确认用户事实的摘要压缩 | 不丢命题，不改含义；优先只重编译画像 |
| 不同记录的语义合并 | 提案；证据、范围和时间条件一致后再批准 |
| 因长期未使用删除用户喜好 | 禁止 |
| 用户明确纠正一个旧事实 | 立即更新，旧版本标为 superseded |
| 模型推断与用户明确事实冲突 | pending，不覆盖 |
| 超出已明确期限的临时上下文 | 失效/归档，不混同永久忘记 |
| 验证过的任务经验变成 Skill | 单独提案、测试、版本化 |
| 冷技能或阶段性项目记录 | 可逆归档，依赖与置顶保护 |
| 置顶/用户确认的重要约束自动删除或改义 | 禁止 |
| 用户明确要求忘记 | 立即停止使用，并启动对应清理 |

“长期未召回”只能说明可能不需要放进热上下文，不能说明“对用户没价值”。

## 8. 删除、归档、替代与遗忘分开

```text
candidate → pending_confirmation / active
active → superseded     用户/可信事实已更新
active → archived       冷数据，仍可受控找回
active → expired        适用期限已结束
任意状态 → deleted      明确遗忘或经授权的保留策略清理
```

### 8.1 自动剪枝优先缩小热上下文

可以把低收益的任务碎片移出热上下文、合并重复记录或归档阶段性材料。明确用户偏好不设置“30 天没问就删”的统一 TTL；项目环境事实应有版本与复查时间；临时承诺依明确期限失效。

压缩当前对话上下文、压缩画像、归档历史、永久遗忘是四种操作，不能用一个“清理记忆”按钮代替。

### 8.2 遗忘屏障：防止重建后复活

用户要求忘记时：

1. 立即禁止该事实继续参与读取和上下文构建。
2. 失效画像、摘要缓存和进行中的旧整理计划。
3. 清理 FTS、向量、待处理任务及派生副本；清理失败时由读取闸门阻断。
4. 保存不含原文的遗忘屏障：作用域、来源谱系、命题签名、截止版本；敏感值可用本地密钥 HMAC，不把被删原文留在“删除日志”里。
5. 抽取、索引重建、归档恢复、备份恢复必须检查屏障；用户以后明确要求重新记住，可以针对新证据重新授权。

一个来源消息可能同时包含苹果和香蕉。忘记苹果后，不能经“香蕉记忆”的整段来源把苹果又注入模型。证据应尽量定位到命题片段；已知派生摘要也要失效或重建。

需要明确边界：删除记忆不必然删除聊天。若提供“彻底删除相关数据”，还必须覆盖聊天保留策略、证据副本、历史 revision、缓存和本地备份；已经发给第三方的请求不能声称由本地删除一并清除了。

这里的数据库硬删除也不等于对 SQLite 空闲页、WAL、操作系统缓存和备份的取证级擦除；产品承诺必须区分应用内不可再用与底层彻底清除。

严格遗忘应在下一次模型调用前移除已识别的相关上下文。无法可靠定位旧上下文时重建会话上下文，而不是保留旧摘要却宣称完全忘记。对未追踪的语义副本不能做不可验证的绝对保证。

### 8.3 回滚不能撤销用户的遗忘意愿

普通归档/合并可撤销；用户明确遗忘后的内容不能通过“撤销上次做梦”恢复。审计中的旧值、备份与来源读取同样需要清理或访问屏障。技能版本恢复与个人数据永久删除不能共用同一保留承诺。

## 9. 数据与模块落点

### 9.1 保持单一事实来源

保留 `memory_entries` 兼容层，逐步增加/规范：主体、事实种类、规范命题键、结构化值、来源类型、状态、revision、有效时间、保护级别。

新增职责表建议：

| 表/实体 | 职责 |
|---|---|
| `memory_evidence` | 消息/产物引用、片段、hash、授权范围 |
| `memory_evidence_links` | 多对多 supports/refutes/derived_from |
| `profile_snapshots` | 带事实 revision 的有预算画像投影 |
| `conversation_summaries` | 历史事件、决策、未完成事项及证据锚点 |
| `memory_change_sets` | 变更提案、风险、前置版本、审核及应用结果 |
| `memory_usage_events` | 召回、注入、使用声明、可验证反馈 |
| `memory_maintenance_runs` | 租约、增量游标、模型、预算、报告 |
| `memory_tombstones` | 防重新学习/恢复的遗忘屏障 |

继续复用 `embedding_documents/jobs/generations`；每个索引文档绑定来源 revision/hash。所有召回结果均回到权威数据检查状态、期限、权限，而非只相信向量返回的 ID。

### 9.2 服务边界

```text
crates/memory/
  facts / evidence / profile / lifecycle
  retrieval / change_set_validator / forgetting / usage

crates/core/
  memory_context_builder
  memory_analysis_runtime    # 抽取/整理模型调用、预算、中止；不进入普通记忆采集回路
  memory_maintenance_runner

crates/tools/
  memory_add/search/read/profile_read/forget 适配器

Electron
  设置、用户审核、变更报告、来源展示；不另持有一套事实写入逻辑
```

记忆 crate 不反向依赖完整 Agent Loop。模型分析通过接口由 core 注入，避免依赖环，也避免“整理器的回答又被采集成新记忆”。

目标新增控制面：`profile.read`、`memory.propose`、`memory.preview`、`memory.apply`、`memory.archive/restore/forget`、`memory.maintenance.status`。名称可调整；关键是所有入口共享同一 Validator。

模型不能自行填写可信的 `origin=explicit_user` 或审批状态。操作来源由宿主/运行时绑定；profile、规则与事实不能通过直接 RPC 绕过权限。

### 9.3 多 Agent 与跨受众

- 同一用户画像可供授权 Agent 使用，但各 Agent 不直接并发改同一 Markdown 文件。
- 一轮请求拿明确的画像版本；修改使用乐观锁＋事务。
- 私聊、群组、外部 IM 分别构造允许披露的画像投影。
- 召回和证据回读都检查权限。可共享事实不自动意味着可公开完整私人来源。
- 设备环境事实按设备/项目限定，不能将某台机器的状态当作用户的永久属性。
- 相同用户标识不意味着跨设备已经同步；本提案不暗含自动云同步。

## 10. 产品界面

从“全部记忆卡片”升级为几个可理解的入口：

1. **关于你**：已确认的偏好、约束、类别、适用范围，支持纠正/临时覆盖/忘记。
2. **项目上下文**：规则、当前决策、失效版本、关联目标。
3. **历史线索**：能打开授权来源，不把摘要冒充原话。
4. **学会的技能**：适用条件、验证记录、使用情况、归档/恢复。
5. **整理记录**：本次为何运行、具体变更、被保护的事实、待确认项、成本和撤销范围。

设置中分别提供“使用已有记忆”“允许当前会话贡献新记忆”“允许后台整理”，支持会话级覆盖。关闭贡献不等于删除旧记忆，关闭读取也不等于同意继续写入。Embedding 的远程发送开关另行控制，不能把“关闭向量”误当作“关闭记忆”。

不以“生成了多少条记忆”作为主要成功提示。只在提交成功后显示“已记住”；仅有候选或等待确认时明确区分。

## 11. 怎样验收“更懂用户”

先用固定跨会话测试集，再允许自动维护。测试目标是行为，而不仅是向量命中。

| 场景 | 预期 |
|---|---|
| 苹果事实＋大量技术噪声，问“我喜欢吃什么” | 读到饮食事实并进入模型上下文 |
| 关闭 embedding 后问同一问题 | 核心画像/类别读取仍可用 |
| 用户说“现在不喜欢苹果了” | 下一轮用新事实；旧计划不能覆盖 |
| 用户另外说“也喜欢香蕉” | 不误删苹果这一独立喜好 |
| 本次要求详细解释，长期偏好简洁 | 本次指令优先，不永久改画像 |
| 转述朋友、举例、提问、外部页面指令 | 不变成当前用户的已确认事实 |
| 明确事实长时间没用到 | 不因低频或不属软件工程而删除 |
| 用户忘记后重建索引、重跑旧抽取、撤销整理 | 已知存储路径不使其复活 |
| 两个用户/不同群组/私人来源 | 不跨权限泄露 |
| 技能缺少成功证据或测试 | 不自动提升为默认执行规则 |
| 整理期间用户手动改记录 | 过期变更拒绝，保留用户的新版本 |
| 审核拒绝／后台任务回滚 | 不误报“已记住/已更新” |

记录：相关事实召回率、回答有证据支持的比例、偏好/约束遵循率、误写与纠正率、遗忘复活测试、权限隔离测试，以及每轮上下文和后台模型成本。

检索次数只能衡量曝光，不能独立决定置信度或重要性。效果无法归因时标 unknown，不能靠 AI 自评把分数越刷越高。

## 12. 最小实现路径：先让已有记忆更有用

以下是**可独立交付的过渡方案，不是第 5–9 节完整事实治理的缩小版**。目标是在不新增表、画像文件、模型调用或后台 Dream Worker 的前提下，让已保存的个人事实更稳定地进入回答，同时减少噪声和误删。估算约 **3–5 个工程日**（含针对性回归，具体以现有测试和数据量为准）；现有中文词法召回、向量融合、embedding 分批、来源展示已存在，**不作为本阶段重复开发项**。

交付后应能做到：用户明确说“我喜欢吃苹果”，另开会话问“我喜欢吃什么”，即使关闭 embedding、同时有大量 Agent 技术摘要，回答仍能使用这条事实；没有来源的记录不能被说成“用户亲口说过”。

### M0：减少自动写入的噪声（约 0.5–1 天）

- `harness-rs/crates/memory/src/lib.rs::ingest_workspace_memories`：默认停止从助手回答中按“必须、项目、API、记忆”等宽泛关键词自动生成 `knowledge`。当前最多取三段的规则容易保存模型复述或泛化建议；先保留现有的**用户明确偏好提取**、手工保存与 `memory_add`，项目知识以后再按明确用户要求或可信任务结果重开写入。`allowKnowledge` 不应被解释为“助手写的任何技术句子都是事实”。
- 不批量删除旧数据，也不把旧 `knowledge` 自动升级为“用户已确认”。用户手工添加、`memory_add` 写入的 user-scope `knowledge` 仍可检索；但当前工具没有可靠的用户原话来源，不伪造 `sourceText`。本步会减少自动获得的项目知识，属于刻意接受的短期取舍。
- 回归：问答/失败检索的助手回复不新增事实；“我喜欢吃苹果”仍写入带原话的 `user_trait`；手工及工具写入不受停用自动提取影响。现有“助手回答生成 knowledge”的测试需随预期行为调整，不应简单删掉断言后失去覆盖。

### M1：给用户事实保留独立的上下文位置（约 1–2 天）

- `harness-rs/crates/core/src/agent.rs::memory_prompt_sections`：继续保留现有词法＋向量检索，但给**当前运行已授权的确切 user scope ID** 单独查询和预算；不要等混合召回的前 40 条、每类前 8 条决定个人事实是否能进入提示词。非 user scope 的 `user_trait` 不能仅因类型名就当作“关于当前用户”。
- 小型常驻位置只放少量（例如最多 4 条）置顶/用户明确保存的重要事实；普通饮食、沟通习惯等不必全部常驻。遇到“我喜欢吃什么”之类个人问题，再按轻量意图类别读取该用户 scope 的有效事实（例如饮食类别匹配现有 tags/title/summary 中的“饮食、口味、喜欢吃、爱吃”等）；可在现有 SQLite 表上新增**有上限、有状态/到期过滤**的查询方法，不要求画像表或新索引。既有 `user_trait` 与 user-scope `knowledge` 都参与候选，但保留来源差异；后者可能来自 `memory_add`，不能因类型为 `knowledge` 就排除或因 scope 为 user 就声称已核实。
- 对旧记录可用规则做有限类别回退；识别不到类别时继续现有混合检索/`memory_search`，不要把“没检索到”说成“用户没有偏好”。用户一旦纠正或删除，下一次模型调用重新查询，不缓存一份无法失效的自由文本画像。多条事实冲突时保留各自原文，不能靠相似度自行删改；必要时指出冲突。
- 将常驻与类别候选合并去重，先控制条数/字符预算再交给现有 `format_memory_prompt_sections`；只给当前请求可见的 ID、摘要、已有来源片段，不注入全量聊天原文。对面向群组/外部受众的场景，不新增私有画像的自动披露；仍需后续受众级权限设计。
- 规则类别和固定预算不保证覆盖所有表达或大量陈年记录；这是当前有意接受的容量边界，不宣称实现了完整用户画像。

### M2：先保护个人事实，再考虑“做梦”（约 0.5–1 天）

- `apps/electron/electron/main-process/ai/memory-compaction.ts`：删除“与软件工程/当前 Agent 无关就删”的指令，不把 user-scope 事实送进现有自动整理计划。
- `harness-rs/crates/memory/src/lib.rs::compact_workspace_memories`：在应用层之外再加一道实际执行校验：**跳过涉及 user scope 的 delete/merge/update**；置顶记录在所有 scope 下也不得被模型合并、改写或删除。保护的是自动整理入口，不应拦截用户在设置页或明确遗忘操作中的手工删除。保留现有人工触发，但不接入定时后台；非用户范围的 AI 整理仍属于待审核能力，不把模型生成的摘要当已验证事实。
- 回归：模型计划包含 user-scope `knowledge`、`user_trait` 或 pinned 条目时，全部保持原样；手工删除仍可用。计划输入过滤只是减少风险，Rust 写入侧保护才是边界。

### M3：用跨会话行为验收，而不是只测 SQL 命中（约 0.5–1 天）

在 `harness-rs/crates/memory/tests/memory_recall.rs` 和 `harness-rs/crates/core/src/agent.rs` 的提示词测试中固定以下场景：

1. 保存“我喜欢吃苹果”后换会话提问；关闭 embedding、混入大量 Agent 摘要和一次“未找到偏好”的旧回复，断言**实际提示词含苹果事实**，而不仅是检索 API 返回苹果。
2. `memory_add` 产生的 user-scope `knowledge` 可进入个人问题的候选；无 `sourceText` 时提示词不能捏造用户原话。置顶的用户事实在无关任务中占有限位置，非置顶事实按相关类别进入。
3. 错误 scope、inactive/过期/已删除条目不进入任何用户事实通道；多个偏好不被单一结果挤掉；助手转述、假设、提问不变成用户事实。
4. 整理后个人事实不变，用户手工删除后下一轮提示词不再带入已删除条目；词法/向量路径的旧回归继续通过。

**上线边界与回退**：这一阶段只提升“已明确保存的事实能够被用上”，不解决来源谱系、条件冲突裁决、语义去重、旧聊天重提取防复活及彻底遗忘。M0 的自动提取开关与 M1 的额外上下文位置应能分别停用；发现错引个人事实时先关额外注入、保留库内数据，避免通过删库回滚。进入完整治理时再按下文 P0–P3 补证据、revision、审核与遗忘屏障，**不能以 M2 的 scope 保护冒充完整安全审计**。

## 13. 完整实施顺序

### P0：先让整理安全

- 去掉“与软件工程无关就删”的判断。
- 区分自动归档与显式遗忘；明确事实、置顶及重要约束由 Rust 保护。
- 整理计划增加 evidence/revision，并提供预览、逐项审核和应用报告。
- 模型未看到可靠来源时，不允许改写用户事实。
- 收敛遗留 `memory.add/search` 兼容入口，避免新旧表各自成为真相。

验收：上述误删、并发覆盖、越权与来源测试通过；未满足前不启用自动删除。

### P1：真正建立用户模型

最小落地不必一次建齐全部新表：先扩展 `memory_entries`，补证据及关联、画像投影和变更集；使用反馈和维护事件可以先以有版本的结构化载荷写入现有 `memory_events`，再按规模拆分。

- 原子事实、来源关系、时间/场景条件、冲突处理。
- 用户画像投影、类别直读、已确认/待确认区分。
- 让当前任务主动使用偏好；修正后下一轮生效。
- 保留词法/向量/历史搜索作为补充，不让个人问题完全依赖向量。

验收：跨会话使用偏好、条件例外、多值偏好和真实来源测试通过。

### P2：上线受控 Dream Worker

- 增量游标、空闲调度、预算、中止、变更台账、遗忘屏障。
- 先 shadow/dry-run，只产出报告；验证结果达到要求后再允许低风险自动应用。
- 个性推断、高风险冲突和破坏性修改继续待确认。

验收：无保护事实误删，无旧计划覆盖，重建/恢复不绕过遗忘，后台成本可控。

### P3：从任务经验形成能力

- 从实际成功和纠错中提炼技能，附前提、验证步骤、版本和回退。
- 技能使用、补丁和失败单独计量；长期不用先归档。
- 保护正在被目标、项目或定时任务引用的技能。

验收：同类任务减少重复试错，而不是技能目录越来越大。

## 14. 旧数据迁移原则

- 不清空现有库，不对旧个人事实做未经确认的批量重分类/删除。
- 旧记录保持可搜索；仅在证据足够时进入已确认画像，否则标 legacy/待验证。
- 来源无法恢复就显示未知，不能由助手生成一段“用户原话”。
- 仅凭记忆文案、ID 前缀或模型给出的高分，不能升级权威等级。
- 增量引入生命周期字段与 DTO，再建立画像投影；完成后才切换自动维护入口。
- 回归需包含已经修复的中文召回、10 条 API 分批、scope 过滤、来源显示等用例。

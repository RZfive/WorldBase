## 一、结论先行

### 当前基线

WorldBase 不是“只有文件工具”的状态。当前 Rust Harness 已经具备：

- ✅ 单执行段最多 128 步的通用 Agent 循环。
- ✅ 上下文压缩，保留目标、最近消息、关键路径和工具结果摘要。
- ✅ 连续只读工具并行。
- ✅ `spawn_subagents` 并行子任务。
- ✅ 文本 patch、项目管理、命令执行和权限控制。
- ✅ Desktop、CLI、Mobile 共用 Rust Harness；移动端使用手写 `dart:ffi`。

当前主要缺口是编码专用能力：

- 🧩 `coding_loop`：缺强制验证、修复状态机和停止策略。
- 🧩 tree-sitter：缺语义定位和结构化增量编辑。
- 🧩 Error Analyzer：缺统一诊断和修复建议。
- 🧩 LSP：缺实时诊断、符号和快速修复。
- 🧩 依赖感知并行写入：缺安全的多文件并发修改调度。

## 三、关键能力详解

### 1. ✅ 通用循环：已有，但不是编码专用闭环

**当前实现**：
- 单执行段最多 128 步。
- 可连续进行工具调用、观察结果、继续下一步。
- 达到段上限后可进入下一执行段。
- 有运行时长、重复调用和完成信号保护。

**仍缺**：
- 编码任务状态没有独立建模。
- 不强制“修改后验证”。
- 不保证“验证失败后必须诊断”。
- 不限制“同一错误重复修复”的轮次。
- 不区分编码任务中的计划证据和验证证据。

**提案 `coding_loop`**：
```text
Plan → Inspect → Edit → Verify → Diagnose → Repair → Verify
                                                   ↘ Blocked
```

**验收重点**：
- 修改后执行验证的任务占比 ≥95%。
- 修复轮次、时间、token 和重复失败均有上限。
- 关闭提案模块时现有循环行为不变。

---

### 2. ✅ 上下文压缩：已有，但可更懂编码

**当前实现**：
- 按模型窗口和周期触发压缩。
- 保留用户目标锚点、最近消息、关键路径、命令、错误和工具结果摘要。
- 长任务切换执行段时继续任务。

**仍缺**：
- 不专门标记“当前失败诊断”。
- 不专门标记“已改文件/未改文件”。
- 代码片段、diff 和 AST 节点可能被均匀截断。
- 缺少压缩后成功率的实证。

**提案增强**：
- 优先保留当前错误、目标符号、相关文件和验证结果。
- 对 diff 和测试失败做结构化摘要。
- 用 A/B 基准验证成功率、token 和重复读取次数。

---

### 3. ✅ 只读并行与子智能体：已有基础

**当前实现**：
- 连续只读工具调用并行。
- `spawn_subagents` 支持独立子任务并行。
- 主智能体等待所有结果后再综合。
- 写操作、命令和未知工具保持串行。

**仍缺**：
- 编码任务的侦察拆分模板。
- 子智能体结果去重和质量评分。
- 文件级依赖图和写冲突检测。
- 并行任务失败后的依赖传播策略。

**提案**：
- 侦察阶段优先并行只读任务。
- 编辑阶段只有无依赖、无冲突的写入才并行。
- 未知依赖默认串行。
- 所有并行结果必须可追溯到任务和文件。

---

### 4. 🧩 语义增量编辑：主要短板

**当前**：
- `patch_project_file` 可做文本级增量修改。
- 比全文重写更安全，但仍依赖旧文本匹配。

**问题**：
- 同名符号和多候选匹配容易歧义。
- 无法直接表达“修改某个方法的错误处理”。
- 格式和语法边界没有结构保证。
- 跨文件重构影响面难判断。

**提案 tree-sitter**：
- 建立符号索引和父节点路径。
- 语义定位候选节点并计算置信度。
- 生成 `EditPlan`，转换为现有文本 patch。
- 歧义、冲突或越界时拒绝写入。
- 解析失败时使用现有文本工具并明确提示。

**目标指标**：
- 语义定位准确率 ≥90%。
- 无关文件改动率相对基线下降 ≥50%。
- 写入失败时原文件保持不变。

---

### 5. 🧩 Error Analyzer：从原始日志到可执行诊断

**当前**：
- `run_project_command` 可执行构建、测试和 lint。
- 原始输出可以进入上下文，但没有统一结构。

**问题**：
- 不同工具输出格式不一致。
- 级联错误和重复错误难处理。
- 修复建议缺少证据和置信度。
- 无法统计错误类型与修复效果。

**提案**：
```rust
// 接口示意，不是当前代码
pub struct Diagnostic {
    pub file: Option<String>,
    pub line: Option<u32>,
    pub column: Option<u32>,
    pub code: Option<String>,
    pub message: String,
    pub severity: Severity,
    pub evidence: String,
}
```

**目标指标**：
- 可结构化解析的失败日志 ≥90%。
- 高置信度修复建议验证通过率 ≥70%。
- 低置信度建议不自动写入。

---

### 6. 🧩 LSP：实时反馈能力

**当前**：
- 主要依赖命令执行后的输出。
- 没有语言服务器诊断、符号和快速修复。

**提案**：
- 接入诊断、符号、定义、引用和快速修复。
- 统一转换为 Error Analyzer 诊断结构。
- LSP 仅作为可选高置信度输入。

**目标指标**：
- 常见项目的 LSP 诊断可转换为统一结构。
- LSP 不可用时不影响现有验证路径。
- 不新增第二套 Harness。

---

### 7. 🧩 依赖诊断：从错误到修复计划

**当前**：
- 能观察依赖命令失败。
- 缺 manifest/lockfile 结构化分析。

**提案**：
- 解析依赖清单和锁定文件。
- 识别缺失包、版本约束和冲突。
- 生成修复计划和验证命令。
- 网络或仓库不可用时明确说明阻塞原因。

## 四、内部基准设计

### 1. 任务集

建议建立 50-100 个内部任务，覆盖：

| 类型 | 数量建议 | 示例 |
|------|----------|------|
| 单文件新增 | 10-15 | 新增函数、类型、测试 |
| 单文件修复 | 15-20 | 编译错误、lint、测试失败 |
| 多文件修改 | 15-20 | 接口变更、调用方同步 |
| 重构 | 10-15 | 重命名、提取函数、移动模块 |
| 依赖问题 | 5-10 | 缺失依赖、版本冲突 |
| 长任务 | 5-10 | 超过单段 128 步或多轮验证 |
| 失败/取消 | 5-10 | 不可恢复错误、预算耗尽、用户取消 |

### 2. 环境固定项

- 代码仓库版本和初始 commit。
- Rust 工具链版本。
- 模型及参数。
- 温度、超时、最大 token、最大修复轮次。
- 网络状态和包缓存。
- 是否启用提案模块。
- 评分脚本版本。

### 3. 指标

| 指标 | 定义 |
|------|------|
| 任务成功率 | 通过全部验收测试的任务数 / 总任务数 |
| 首次通过率 | 第一次修改后通过验收的比例 |
| 修复成功率 | 验证失败后经修复最终通过的比例 |
| 无关改动率 | 非目标文件/无关代码行变更占比 |
| 验证覆盖率 | 修改后执行验证的任务比例 |
| 诊断解析率 | 可结构化解析的失败日志比例 |
| 平均修复轮次 | 每个任务进入 Repair 的平均次数 |
| 平均耗时 | 从任务开始到终止的 wall-clock 时间 |
| Token 消耗 | 输入、输出、缓存和压缩后的总量 |
| 重复读取率 | 同一文件/片段被重复读取的比例 |
| 并行收益 | 并行版本相对串行版本的耗时比 |
| 稳定性 | 超时、崩溃、悬挂和取消失败次数 |

### 4. A/B 对照

| 对照组 | 配置 | 目的 |
|--------|------|------|
| A | 当前 Rust Harness | 基线 |
| B | + `coding_loop` | 验证闭环收益 |
| C | B + tree-sitter | 验证编辑精度 |
| D | C + Error Analyzer | 验证诊断和修复收益 |
| E | D + LSP/依赖诊断 | 验证反馈与依赖能力 |

每轮至少重复 3 次，报告均值、中位数和失败分布。不得只报告最佳结果。

## 六、4 周快速验证（提案）

如果资源有限，先做 4 周验证，不直接承诺完整 16 周范围。

### 第 1 周：基线

- 固定 20-30 个代表性任务。
- 采集当前成功率、耗时、token、验证覆盖和失败类型。
- 回归 128 步循环、压缩、只读并行和子智能体。

### 第 2 周：最小 `coding_loop`

- 只实现 Plan → Edit → Verify → Complete。
- 验证失败时记录结构化原因。
- 暂不自动修复复杂错误。

### 第 3 周：最小诊断

- 解析构建和测试错误。
- 覆盖最常见的 10 类失败。
- 只对高置信度问题生成建议。

### 第 4 周：评估

- 对比基线成功率、验证覆盖率和无关改动率。
- 判断是否继续投入 tree-sitter 和完整 Error Analyzer。
- 输出 go/no-go 报告。

**4 周验证不包含**：
- 完整语义编辑。
- LSP。
- 安全并行写入。
- 多语言全面覆盖。

## 九、竞品观察

### Codex

可借鉴点：
- 工具循环与验证紧密结合。
- 工具调用结果被持续观察和再利用。
- 上下文和成本控制成熟。

可借鉴点：
- 编辑器/语言服务联动体验好。
- 增量修改和最小 diff 表现突出。
- 诊断反馈路径短。

### Cline

可借鉴点：
- 开源架构灵活。
- 工具协议扩展方便。
- 本地化与可配置性强。

## 十、风险与约束

| 风险 | 影响 | 缓解 |
|------|------|------|
| 基准不可复现 | 高 | 固定环境、任务和评分脚本 |
| 语义定位歧义 | 高 | 多候选时拒绝写入并给出证据 |
| 自动修复误改 | 高 | 仅高置信度、必须验证、可回滚 |
| 并行写入冲突 | 高 | 依赖图 + 文件锁 + 默认串行 |
| LSP 环境不一致 | 中 | 作为可选输入，不作为唯一诊断来源 |
| FFI ABI 漂移 | 高 | 版本化 C ABI、两端冒烟测试 |
| 范围膨胀 | 高 | 先 P0，4 周验证后决定后续 |

## 十一、最终建议

1. **先锁定基线**：现有 128 步循环、上下文压缩、只读并行和子智能体都是资产，必须先有回归保护。
2. **优先做 `coding_loop`**：把“修改后验证”和“失败后诊断”变成确定性策略。
3. **再做 tree-sitter 和 Error Analyzer**：一个提升定位精度，一个提升失败恢复效率。
4. **LSP 与依赖诊断后置**：它们是增强项，不应阻塞 P0 闭环。
5. **保持 Rust-only**：所有能力进入 `harness-rs/`，移动端继续手写 `dart:ffi`。

**最终判断**：方向正确，但必须以内部基准为准，逐阶段验收，不能把提案目标写成当前已实现能力。

# WorldBase Agent vs. Claude Code —— 架构对比文档

> 目的：把 WorldBase 内置编码 Agent（`apps/electron/src/main/ai-engine/`）与官方 Claude Code（v2.1.88 反编译源码）逐层拆开对比，作为《编码能力优化指南》的事实基础。
>
> 对比基准：`/Users/tanyafang/Downloads/claude-code-source-code-main`（Claude Code v2.1.88，unbundled TypeScript 源码）。
>
> 本文只描述「现状与差异」，不给改造方案；改造方案见 [02-编码能力优化指南.md](02-编码能力优化指南.md)。

---

## 0. 一句话结论

两者的**骨架是一样的**（while 循环 + 工具分发 + 多轮 tool-use），WorldBase 的工具**覆盖面也不窄**。真正拉开差距的是三个「内功」层面：

1. **工具的行为质量** —— 尤其是「编辑文件」用行号补丁而非精确字符串匹配，「读文件」不带行号，「搜索」是纯 JS 而非 ripgrep，「执行命令」是严格白名单。
2. **系统提示词的定位** —— WorldBase 的提示词 95% 在讲「如何在 WorldBase 里生成 Next.js 项目」，几乎没有讲「如何做通用软件工程」（怎么读代码、怎么改、什么时候并行、什么时候停）。
3. **模型层与上下文工程** —— 没有 prompt caching、温度写死 0.7、用「字符数 / 4」估算 token、压缩是「摘要 + 保留最近 N 条」的粗粒度策略。

## 1. 两个项目分别是什么

| | WorldBase | Claude Code v2.1.88 |
|---|---|---|
| 形态 | Electron + Vue3 桌面应用，"AI-powered project generator and manager" | CLI（Bun 编译为 Node ≥18 单文件 `cli.js` ~12MB） |
| Agent 代码位置 | [apps/electron/src/main/ai-engine/](../../apps/electron/src/main/ai-engine/) | `src/`（~1884 个 .ts/.tsx，~51 万行；`query.ts` 单文件 785KB） |
| 模型接入 | OpenAI 兼容 `/chat/completions`（自写 fetch） | Anthropic Messages API（`services/api/claude.ts`，streaming） |
| 主要使用场景 | 在 App 内一键生成 / 迭代 Next.js 项目 | 在任意代码仓库里做通用软件工程 |
| 工具数量 | ~40（含大量项目生命周期工具） | ~40+ 内置（+ MCP 动态工具） |

> 关键差异从这里就开始：WorldBase 是「项目生成器」，Claude Code 是「代码工程师」。下文很多差距都源于这个定位差异。

## 2. 整体架构分层对比

### WorldBase

```
渲染层 (Vue)  apps/electron/src/renderer/components/chat/*
      │ IPC
主进程  apps/electron/src/main/ai-engine/
  AIEngine            ai-engine.ts          每次请求 new 一个 AgentCore，注入 provider 配置
    └─ AgentCore      agent/agent-core.ts   思考→行动→观察 主循环 + 压缩 + 循环检测
         ├─ OpenAIProvider  providers/openai-provider.ts   OpenAI 兼容 fetch / 流式
         ├─ Tools           agent/tools/*.ts                ~40 个工具
         ├─ PermissionEngine agent/permissions/permission-engine.ts
         ├─ PlanEngine       agent/plan-mode.ts
         ├─ LoopDetector     agent/loop-detector.ts          SHA-256 去重
         ├─ SkillEngine      agent/skill-engine.ts
         ├─ SubagentService  agent/subagent-service.ts       并行子 agent
         ├─ CostTracker      cost-tracker.ts
         └─ MemoryEngine     memory/memory-engine.ts         跨会话记忆（SQLite）
```

### Claude Code

```
入口  cli.tsx → main.tsx (REPL) / QueryEngine.ts (headless/SDK)
  QueryEngine
    ├─ fetchSystemPromptParts()    组装分段、可缓存的 system prompt
    ├─ processUserInput()          处理 /命令
    └─ query()                     主 agent 循环（最大文件）
         ├─ StreamingToolExecutor  并发安全/串行分区执行
         ├─ autoCompact()          上下文压缩（summary + boundary marker）
         ├─ canUseTool()           hooks → 规则 → 交互式授权
         └─ runTools()             工具编排
  Service 层：api/claude.ts、compact/、mcp/、analytics/、plugins/
  Task 层：LocalShellTask / LocalAgentTask / RemoteAgentTask / DreamTask
  State 层：AppStateStore（permission context、fileHistory、fastMode…）
```

**结论**：分层思路高度一致。Claude Code 多出来的是 **Task 层（后台/远程任务）**、**State 层（文件历史快照、权限上下文）**、以及 **hooks/plugins** 这类生产级扩展点。这些不是「编码能力」的核心瓶颈，先放后面。

## 3. Agent 主循环对比

两边都是经典 agent loop。WorldBase 的实现见 [agent-core.ts](../../apps/electron/src/main/ai-engine/agent/agent-core.ts) 的 `runStream()`。

| 维度 | WorldBase | Claude Code |
|---|---|---|
| 循环结构 | `while(true)`：请求 → 有 tool_calls 则执行 → push 结果 → 续；否则结束 | 同构（README「THE CORE LOOP」） |
| 流式 | ✅ `chatCompletionStream`，token / thinking / tool_calls 事件 | ✅ 全链路 AsyncGenerator |
| 多工具并行执行 | ❌ **串行 for 循环**逐个执行 tool_calls（agent-core.ts:868） | ✅ `StreamingToolExecutor` 区分「并发安全/串行」分区并行跑 |
| 流式重试 | ✅ `maxStreamRetries=3`，指数退避（agent-core.ts:804） | ✅ `withRetry` |
| 单段迭代上限 | `maxIterations=128`，到顶后自动压缩并「续跑」 | 由 compaction 驱动，无硬性段概念 |
| 周期性压缩 | `proactiveCompressionInterval=16`（每 16 轮强制压一次） | 按 token 阈值触发 autoCompact |
| 循环检测 | ✅ 指纹去重 + `LoopDetector`(SHA-256)（agent-core.ts:737-743） | 主要靠模型自身 + 提示词「失败先诊断再换策略」 |
| 参数容错 | ✅ 很强：`_parseToolArguments` 会修复被 ```json 包裹、半截、多段 JSON 的工具参数（agent-core.ts:282-479） | 工具参数走 Zod 校验，模型重试 |
| 兜底续跑 | ✅ `[AUTO_CONTINUE]` 系统指令让模型基于最近结果继续，不重复已完成步骤 | 由 compaction + 提示词处理 |

**结论**：WorldBase 的循环工程化其实做得很扎实（参数修复、循环检测、自动续跑都有，甚至比 Claude Code 更「防御式」）。**唯一明显的能力损失是：tool_calls 串行执行**，模型即使想并行读 5 个文件也会被排队。

## 4. 模型调用层对比

WorldBase：[openai-provider.ts](../../apps/electron/src/main/ai-engine/providers/openai-provider.ts)。

| 维度 | WorldBase | Claude Code |
|---|---|---|
| 协议 | OpenAI 兼容（也兼容 DeepSeek、Azure、图像模型） | Anthropic Messages API 原生 |
| temperature | **硬编码 0.7**（openai-provider.ts:276） | 走模型默认 / 任务相关设置（编码常用 1 + thinking） |
| thinking / reasoning | ✅ `reasoning_effort`（low/medium/high/max → 各家映射） | ✅ 原生 extended thinking |
| **prompt caching** | ❌ **完全没有**。每轮把完整 system prompt + 全部工具 schema 重新发送 | ✅ `cache_control` 断点 + `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 把「静态可缓存前缀」与「动态后缀」分开（prompts.ts:114） |
| 上下文窗口 | 默认 **32000**，可由设置覆盖（openai-provider.ts:209） | 跟随实际模型（200K / 1M） |
| token 计数 | **字符数 / 4 估算**（agent-core.ts:97, `_estimateTokens`） | 真实用量来自 API usage，压缩按真实 token |
| 用量回传 | ✅ `stream_options.include_usage` → CostTracker | ✅ usage / cost |
| 多模态 | ✅ 输入图片、图像生成 / 编辑（DALL·E、gpt-image、Responses API） | ✅ 图片 / PDF / notebook |

**结论**：模型层是差距重灾区。三件事直接拖累编码表现与成本：
- **无 prompt caching** → 长会话每轮都全量重发，既贵又慢，也逼着团队「不敢写长 system prompt、不敢挂太多工具」，反过来又削弱能力。注意 [cost-tracker](../../apps/electron/src/main/ai-engine/cost-tracker.ts) 的 pricing 类型里**已经预留了 `cacheReadPerMillion` 字段**（ai-engine.ts:162），说明缓存是「想做但还没接」。
- **temperature 写死 0.7** → 对需要确定性的编辑/重构任务偏随机；对 gpt-5 / o 系列等「只接受 temperature=1」的模型甚至可能被拒。
- **token 用字符 /4 估算** → 压缩触发点不准，要么过早砍上下文（丢信息），要么过晚（超窗报错）。

## 5. 工具系统对比

### 5.1 覆盖度总览

WorldBase 的工具注册见 [tools/index.ts](../../apps/electron/src/main/ai-engine/agent/tools/index.ts)。**覆盖面其实相当全**：

| 能力域 | WorldBase | Claude Code | 差距性质 |
|---|---|---|---|
| 读文件 | `read_project_file` | `Read` | ⚠️ 行为差（见 5.2） |
| 写文件 | `write_project_file` | `Write` | 基本对齐 |
| 改文件 | `patch_project_file`（行号区间） | `Edit`（精确字符串匹配）+ `replace_all` | ❗ **本质差距**（见 5.2） |
| 批量改 | ❌ 无 | （Edit 支持 replace_all） | 缺多点原子编辑 |
| 删文件 | `delete_file` | （Bash / Write） | 对齐 |
| 文件名搜索 | `glob_search` | `Glob` | 基本对齐 |
| 内容搜索 | `grep_search`（纯 JS） | `Grep`（ripgrep） | ❗ 行为差（见 5.2） |
| 执行命令 | `run_project_command`（白名单）+ `local_run_command`（需授权） | `Bash`（完整 shell + 后台 + sandbox） | ❗ **能力差距**（见 5.2） |
| 后台进程 | `get_project_command_status`（超时转后台） | `Bash run_in_background` + `BashOutput` + `KillShell` | 部分对齐 |
| Todo | `manage_todo_list` | `TodoWrite` | ⚠️ 描述弱（见 5.3） |
| 计划模式 | `enter/exit_plan_mode` | `EnterPlanMode/ExitPlanMode` | 对齐 |
| 子 agent | `spawn_subagents`（并行） | `Agent/Task`（类型化 + fork + worktree + 后台） | ⚠️ 能力差（见第 8 节） |
| Web 搜索 | `web_search` | `WebSearch` | 对齐 |
| 抓网页 | `fetch_webpage` | `WebFetch`（AI 抽取） | 略弱 |
| Skill | `run_skill/list_skills/install_skill` | `SkillTool` | 对齐 |
| MCP | `install_mcp_server` + 动态工具注册 | MCPTool + 5 种 transport | 对齐 |
| 提问用户 | ❌ 无独立工具 | `AskUserQuestionTool` | 缺 |
| 项目生命周期 | `create/rebuild/finalize/clear_build_flag/start/restart/open_project_app/get_status/get_logs/list_projects` | ❌（不需要） | WorldBase 独有 |
| 数据/文档 | `call_api/query_db/analyze_data/read_document` | ❌ | WorldBase 独有 |
| 浏览器内页 | `read_current_page/interact_current_page` | （WebBrowserTool 特性门控） | WorldBase 独有 |
| 定时/工作区 | `create_scheduled_task/create_agent/create_agent_group` | ScheduleCronTool / 多 agent | 各有侧重 |

> 重要认知：**「补工具」不是主要矛盾**。WorldBase 缺的工具不多（`AskUserQuestion`、`MultiEdit`、`LSP`、`NotebookEdit` 等），真正的问题是**已有的核心工具行为不够「编码友好」**。

### 5.2 四个核心工具的「行为质量」差距（编码能力的命门）

#### (a) 改文件：行号补丁 vs 精确字符串匹配 —— **最关键**

WorldBase 的 [tool-patch-file.ts](../../apps/electron/src/main/ai-engine/agent/tools/tool-patch-file.ts)：

```
patches: [{ start_line, end_line, content }]   // 按 1-based 行号区间替换
```

Claude Code 的 `Edit`（FileEditTool/prompt.ts）：

```
Performs exact string replacements in files.
- 编辑前必须先 Read（否则报错）
- old_string 在文件中不唯一就 FAIL（要么加上下文，要么 replace_all）
- 保留行号前缀之后的精确缩进
```

为什么这是命门：
- 行号会**漂移**。模型先读到某段，改完上面几行后，下面的行号全变了。WorldBase 用「倒序应用补丁」缓解了同一批次内的漂移，但**跨工具调用、跨轮次的行号失配**它管不了。
- 模型**不擅长数行号**。而 WorldBase 的 `read_project_file` **又不返回行号**（见下条），等于让模型「闭着眼睛数行号去改」。
- 精确字符串匹配把「定位」变成模型最擅长的「复述一小段它刚读到的代码」，并用「不唯一即失败」兜底正确性。这是 Claude Code 编辑几乎不出错的核心原因。

#### (b) 读文件：不带行号 vs `cat -n` 行号

WorldBase 的 [tool-read-file.ts](../../apps/electron/src/main/ai-engine/agent/tools/tool-read-file.ts) 返回的是 `lines.slice().join('\n')` —— **纯内容，无行号**；每段最多 400 行（`MAX_SEGMENT_LINES`），默认 200。

Claude Code 的 `Read`（FileReadTool/prompt.ts）：
- `cat -n` 格式，**行号从 1 开始**（`LINE_FORMAT_INSTRUCTION`）；
- 默认一次读 **2000 行**（`MAX_LINES_TO_READ`），鼓励「直接读整文件」；
- 支持图片、PDF（分页）、Jupyter notebook。

两条叠加形成恶性循环：**读不到行号 → 行号补丁必然容易错**。

#### (c) 内容搜索：纯 JS vs ripgrep

WorldBase 的 [tool-grep-search.ts](../../apps/electron/src/main/ai-engine/agent/tools/tool-grep-search.ts)：
- 自己 `readline` 逐文件逐行读，**强制 `'i'` 大小写不敏感**（无法精确区分大小写）；
- 无输出模式（只有 content+context），无 `type` 过滤（只有 glob include），跳过 >2MB 文件，硬编码忽略目录列表；
- 性能与正确性都弱于 ripgrep。

Claude Code 的 `Grep`（GrepTool/prompt.ts）：`A powerful search tool built on ripgrep`，支持完整正则、`glob`/`type` 过滤、三种输出模式（content / files_with_matches / count）、`multiline`。

#### (d) 执行命令：白名单 vs 完整 shell

WorldBase 的 [tool-run-command.ts](../../apps/electron/src/main/ai-engine/agent/tools/tool-run-command.ts)：
- **白名单**（`PROJECT_COMMAND_WHITELIST`），npm 只允许 `install/ci/test/run <短任务>`，git 只允许 `status/diff/log/show/rev-parse/branch`；
- **禁止 shell 控制符** `; & | < > \``（validateProjectCommand:421）—— 不能管道、不能 `&&` 串联；
- 每条命令独立进程，**无持久 shell 状态**；stdout 截断 20000 字符。
- 另有 `local_run_command`（走用户 shell、需授权）作为「逃生通道」。

Claude Code 的 `Bash`（BashTool/prompt.ts）：完整 shell（工作目录持久）、`run_in_background`、可配 timeout、sandbox、内置 Git 安全协议、并行调用引导、「不要用 Bash 跑 find/grep/cat，用专用工具」。

> 取舍说明：WorldBase 是「应用内沙箱」，收紧命令面**是合理的产品安全选择**。但它在「做真实工程」时是硬约束——跑不了任意测试器、linter、类型检查、脚手架。优化方向不是「无脑放开」，而是「**受控放开**」（见优化指南 §2.4）。

### 5.3 工具描述（给模型看的 description）质量差距

这是最容易被忽视、但**性价比极高**的差距。对比同一类工具的 description 长度与信息量：

| 工具 | WorldBase 描述 | Claude Code 描述 |
|---|---|---|
| 读文件 | 一句话："Read file content... Large files can be read in line-based segments." | 十余条 Usage：绝对路径、2000 行、行号格式、图片/PDF/notebook、空文件提醒…… |
| 改文件 | 两句话讲行号区间语义 | 「先读后改、唯一性失败、缩进对齐、优先改不新建、别加 emoji、replace_all 用法」 |
| Todo | 一句话："Create or update the working todo list..." | **整页**：何时用/何时不用 + 6 个正反例 + 状态机规则（恰好一个 in_progress、完成即标记不批量） |
| 搜索 | 一句话 | ripgrep 语法、输出模式、转义、multiline、何时改用 Agent |

Claude Code 把「**工具该怎么用、什么时候用、什么时候别用**」全写进了 description（模型每轮都看得到），而 WorldBase 大量这类引导散落在 system prompt 里、或者干脆没有。description 是「贴着工具的局部最优引导」，比塞进 system prompt 更稳。

## 6. 系统提示词结构对比

WorldBase：[system-prompt.ts](../../apps/electron/src/main/ai-engine/agent/prompts/system-prompt.ts) `getSystemPrompt()`，单个大模板字符串 + 末尾拼接环境上下文。

Claude Code：`src/constants/prompts.ts` `getSystemPrompt()`，由一系列 `getXxxSection()` **可组合分段**拼装，并插入缓存边界标记。

### 6.1 段落构成对比

| Claude Code 段落 | 作用 | WorldBase 是否有对应 |
|---|---|---|
| `# (intro)` 你是软件工程交互式 agent + 网络安全约束 + 不臆造 URL | 角色定位（**软件工程**） | ⚠️ 有角色，但定位是「WorldBase 助手 / 项目生成」 |
| `# System` markdown 输出、权限模式、system-reminder、**提示注入要上报**、hooks、自动压缩 | 运行机制 | 部分（无注入防护、无 hooks 概念） |
| `# Doing tasks` **核心**：读后再改、不过度工程、最小化注释、不无故新建文件、失败先诊断、安全、如实汇报 | 软件工程方法论 | ❌ **几乎没有**（被「新建项目工作流」「项目生成规则」占满） |
| `# Executing actions with care` 可逆性/影响面、危险操作先确认、授权不外延 | 行动安全 | 部分（有「本地操作需授权」，但无「可逆性/影响面」框架） |
| `# Using your tools` 优先用专用工具而非 Bash、**并行工具调用**、用 Todo 管理 | 工具策略 | ⚠️ 有「工具优先级」，但偏项目工具；**无并行调用引导** |
| `# Tone and style` 不用 emoji、简洁、`file_path:line_number` 引用、tool 调用前不要加冒号 | 沟通风格 | 部分（有 LaTeX/Mermaid/中文，但无 `file:line`、无简洁约束、反而鼓励 HTML） |
| `# Output efficiency` 直接给结论、别绕圈、极简 | 输出效率 | ❌ 无 |
| `# Environment` cwd/git/平台/模型/知识截止 | 环境注入 | ✅ 有（environment-context.ts），偏命令能力清单 |
| 动态段：session 指引、CLAUDE.md 记忆、语言、output style、MCP 指令、scratchpad | 会话级 | 部分（skill/plan/记忆有，但无 CLAUDE.md、无 scratchpad） |

### 6.2 定位差异（一眼看穿的根因）

WorldBase 的 system prompt 里，**关于「怎么做软件工程」的内容几乎为零**，绝大篇幅是：
- New project workflow（先出 PRD → 确认 → `create_project` → 迭代 → `rebuild` → `open_project_app`）
- Project generation rules（Next.js App Router、`output:'standalone'`、dataSchema、不许自带 SQLite……）
- Runtime gotchas / Avoiding loops / Compatibility（大量 WorldBase 平台特有的坑）

这套提示词是为「**在 WorldBase 里量产 Next.js App**」高度优化的。一旦任务变成「读懂这段代码并修个 bug」「重构这个模块」，模型得不到任何「软件工程怎么做」的引导——这正是**「同一个模型在这个 agent 下编码不如 Claude Code」的最大单一原因**。

### 6.3 缓存友好度

Claude Code 用 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY`（prompts.ts:114）把 prompt 切成「静态可全局缓存前缀」+「动态后缀」，并刻意把会变的内容（MCP 指令、agent 列表）移到边界之后或做成 attachment，避免每次变动都击穿缓存。WorldBase 的 prompt 没有这种「静/动分离」意识（不过它本来也没接缓存）。

## 7. 上下文管理对比

| 维度 | WorldBase | Claude Code |
|---|---|---|
| 触发 | token 估算 ≥ `contextWindow - headroom`（15%，2K~8K）或每 16 轮强制 | token 超阈值触发 autoCompact |
| 估算精度 | 字符 / 4（agent-core.ts:1078） | API 真实 usage |
| 压缩方式 | 让模型把历史压成 ≤1500 字符英文摘要，然后 `[CONTEXT_SUMMARY]` + 保留最近 N 条（N ∈ {6,4,2,0}）（agent-core.ts:1006-1033） | 结构化摘要（多段）+ `compact_boundary` 标记 + 保留近期全保真消息；另有 snipCompact / contextCollapse（特性门控） |
| 记忆 | MemoryEngine：跨会话记忆，但靠**正则启发式**抽取用户特征（memory-engine.ts:141-166），存 SQLite | CLAUDE.md（用户自写、按目录懒加载）+ memdir |
| 工具结果存储 | `ToolResultStorage` 处理超大输出（截断/落盘） | 工具结果裁剪 + Function Result Clearing（特性门控） |

**结论**：WorldBase 的压缩「能跑、不崩」，但**摘要会丢结构**（1500 字符上限对长编码会话偏激进），且**估算不准导致触发点不稳**。MemoryEngine 思路新颖但正则抽取脆弱，和 Claude Code「用户显式写 CLAUDE.md」是两种哲学——前者自动但易错，后者可控但要用户写。

## 8. 子 Agent / 并行对比

WorldBase：[subagent-service.ts](../../apps/electron/src/main/ai-engine/agent/subagent-service.ts) + [tool-spawn-subagent.ts](../../apps/electron/src/main/ai-engine/agent/tools/tool-spawn-subagent.ts)。

| 维度 | WorldBase | Claude Code |
|---|---|---|
| 并行 | ✅ `spawn_subagents` 一次起多个、`Promise.all` 全部跑完才返回 | ✅ 一条消息多个 Agent 调用并发 |
| 隔离 | ✅ 每个子 agent 独立 AgentCore、独立历史 | ✅ 独立 messages[]，另有 fork（共享缓存）/ worktree / remote |
| 嵌套 | ✅ 限制 `MAX_SUBAGENT_NESTING_DEPTH=2`（ai-engine.ts:75） | ✅ 受控 |
| **专门化类型** | ❌ **无**。子 agent 用的还是同一套（项目生成向）system prompt | ✅ Explore / Plan / code-reviewer / general-purpose… 每种有定制 whenToUse + 工具白名单 |
| 后台运行 | ❌ 阻塞直到全部完成 | ✅ `run_in_background` + 完成通知 |
| 续聊 | ❌ 一次性 | ✅ `SendMessage` 按 ID 续聊 |
| prompt 写法引导 | 简短 | 大段「像介绍给刚进门的同事一样写 prompt」「绝不把综合判断甩给子 agent」 |
| worktree 隔离 | ❌ | ✅ `isolation:"worktree"` |

**结论**：WorldBase 的并行调度本身可用，但**子 agent 没有「专门化」**——派一个子 agent 去「探索代码库」时，它带着满屏「怎么生成 Next.js 项目」的提示词，既浪费上下文又分散注意力。

## 9. 权限 / 安全对比

| 维度 | WorldBase | Claude Code |
|---|---|---|
| 工具授权 | `PermissionEngine` + 本地敏感操作 `authMode`（strict/...）+ 渲染层确认弹窗 | 规则引擎（alwaysAllow/Deny/Ask）+ PreToolUse hooks + 交互式弹窗 |
| 计划模式 | `PlanEngine` 屏蔽写操作 | EnterPlanMode/ExitPlanMode |
| 提示注入防护 | ❌ 提示词未要求上报可疑注入 | ✅ system prompt 明确「疑似注入要先报告用户」 |
| hooks | ❌ | ✅ settings.json 可配 PreToolUse/PostToolUse 等 |
| 危险操作哲学 | 「本地操作需授权」 | 「可逆性 / 影响面 / 授权不外延」成体系 |
